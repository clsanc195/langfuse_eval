The Problem

Production LLM applications need observability. Three platforms compete to solve it. Choosing well affects developer velocity, evaluation rigor, hosting cost, and vendor lock-in.

Goal: Build the same agent once. Trace it through all three platforms. Compare what we get — empirically, side-by-side, with the same code, the same data, the same prompts.

The Three Contenders

Langfuse

OSS, MIT-licensed, self-hostable. Framework-agnostic. Cloud and on-prem.

langfuse.com

LangSmith

Built by LangChain. SaaS-first, deepest LangGraph integration, most polished UX.

smith.langchain.com

Galileo

Evaluation-first. Auto-metrics on every trace. Only platform with in-request guardrails.

app.galileo.ai

Our Approach

Built once. Ran three times.

  • One LangGraph agent — a permission-checking helpdesk bot
  • Four tools — chained by dependency
  • Five scenarios — covering 1 / 2 / 3 / 4 tool calls + an error path
  • Identical instrumentation pattern across all three platforms
  • Prompts pulled from each platform's registry at runtime
  • Datasets registered in each platform

The Agent

LangGraph ReAct loop — a single agent node + tool node + conditional routing

Conditional edge: if last AIMessage contains tool_calls → tools, else → END.

Instrumentation Effort

For a LangGraph agent, how much code does each platform require?

Langfuse

from langfuse.langchain import CallbackHandler

agent.invoke(state, config={
  "callbacks": [CallbackHandler()]
})

1 callback + 3 env vars

LangSmith

# no code change

os.environ["LANGSMITH_TRACING"] = "true"
# + LANGSMITH_API_KEY
# + LANGSMITH_PROJECT

3 env vars, zero code

Galileo

from galileo.handlers.langchain import GalileoCallback

agent.invoke(state, config={
  "callbacks": [GalileoCallback()]
})

1 callback + 3 env vars

Outside LangChain code, all three require explicit instrumentation: Langfuse @observe, LangSmith @traceable, Galileo @log.

Scoring & Evaluation

All three support auto-running evaluators. The difference is what runs by default.

Setup effortWhat runs by default
Langfuseconfigure: model + prompt + filter + samplingnothing — opt-in
LangSmithconfigure: Online Evaluator rulenothing — opt-in
Galileozero configTool Selection · Action Completion · Context Adherence · Instruction Adherence · Tool Error Rate · Hallucination · Toxicity · PII

Once configured, Langfuse and LangSmith evaluators run server-side on every matching trace, the same way Galileo's auto-metrics do. The real choice is whether the defaults pick the rubric for you, or whether you pick it yourself.

Galileo's Headline Feature

Auto-metrics on every trace. No config, no prompt template, no sampling rate.

MetricWhat it measures
Tool Selection QualityDid the agent pick correct tools?
Action CompletionDid the multi-step task finish?
Context AdherenceDid the response stay grounded in tool outputs?
Instruction AdherenceDid it follow the system prompt?

Trade-off: opinionated defaults catch obvious problems out of the box; can be noise for teams with specific quality rubrics.

Where Each Uniquely Wins

Langfuse

  • Only OSS / free self-host
  • Mutable label pointers for prompt deployment
  • Both raw-string AND chat prompt formats
  • Most mature OTEL ingestion
  • Full local dev via docker
  • HIPAA via self-host control

LangSmith

  • Zero-config LangChain integration
  • Threads UI for chat debugging
  • Pairwise experiment comparison
  • Public Prompt Hub
  • Dataset splits
  • Trace-aware Playground
  • Most polished monitoring

Galileo

  • Auto-metrics on every trace
  • Galileo Protect — only in-request guardrails
  • Log Streams within a project
  • Synthetic dataset generation
  • Built-in PII detection
  • ChainPoll hallucination method
  • Continuous learning on metrics

Honest Weaknesses

Langfuse

UI polish trails LangSmith. Monitoring dashboards less mature. Self-host = self-operate (cost moves from license to ops).

LangSmith

SaaS-only at the community tier. No free self-host. Vendor-tied to LangChain even though it works elsewhere via @traceable.

Galileo

Work-email signup gate. SDK API churn between versions. Documentation lighter than the others. Smaller framework ecosystem. Pricing less transparent.

What This Repo Proves

  • Same LangGraph agent, instrumented for all three platforms — no code branching
  • Prompts pushed to all three registries — content-aware, idempotent push
  • Datasets registered in each platform with the correct per-platform schema
  • Sessions / threads grouping verified end-to-end
  • Programmatic scores attached via SDK (Langfuse, LangSmith)
  • LLM-as-judge auto-evaluators running on every trace (Galileo) or on filtered traces (Langfuse, LangSmith)
  • 5 scenarios × 3 platforms × 11 notebooks — all validated headlessly
